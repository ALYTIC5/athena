## Why this matters

Python appears in 61% of the postings you are targeting, and testing appears in 18%. Tests are how a team lets you change code without fear, and how you show that a function does what you say. For the work you want, the hard part is testing code that calls an API, an LLM or the clock, because those are slow, cost money and give different answers, so interviewers often ask how you would test them.

## Objectives

By the end of this lesson you can:

1. Write tests with pytest, using arrange, act and assert, and test exceptions with `pytest.raises`.
2. Use fixtures and `parametrize`.
3. Replace an external dependency with a fake, and explain fakes versus mocks.
4. Test code that uses time with a fixed clock, and work test first in small steps.
5. Explain unit versus integration tests and what makes a good test.

<Chunk n={1} title="Your first tests">

A **test** is a function that runs your code and checks the result. pytest finds functions named `test_*`, runs each one, and reports the ones whose `assert` fails, showing the values involved. Write each test in three steps: **arrange** (set up the input), **act** (call the code) and **assert** (state what must be true). Test one behaviour per test, name the test after that behaviour, and test values on both sides of a boundary, such as 49 and 50 for a rule that says `>= 50`.

To check that code raises an error, use `with pytest.raises(ValueError):`. The test fails if nothing is raised. Compare floats with `pytest.approx`, because `0.1 + 0.2` is not exactly `0.3`.

**Test-driven development (TDD)** works in small steps. Write a small test and watch it fail, make the smallest change that passes, run all the tests, then tidy the code.

**Worked example.** The function under test, with the two sides of its boundary and the float trap.

```python
def delivery_fee(total: float) -> int:
    if total < 0:
        raise ValueError("total must not be negative")
    return 0 if total >= 50 else 4

print(delivery_fee(49), delivery_fee(50))                  # 4 0: the two sides of the boundary
print(0.1 + 0.2 == 0.3, abs((0.1 + 0.2) - 0.3) < 1e-9)     # False True: compare floats with a tolerance
```

And its tests, as pytest would run them.

```python nocheck="needs pytest"
import pytest
from fees import delivery_fee

def test_small_order_pays_a_fee():
    total = 20                          # arrange
    fee = delivery_fee(total)           # act
    assert fee == 4                     # assert

def test_exactly_fifty_is_free():       # the boundary
    assert delivery_fee(50) == 0

def test_negative_total_is_refused():
    with pytest.raises(ValueError):     # passes only if ValueError is raised
        delivery_fee(-1)
```

<Callout type="misconception" title="Common misconceptions in chunk 1">

- "A test that passes proves the code is right." It proves the code does what the test checks. Break the code on purpose to see that the test fails.
- "Testing the middle of a range is enough." Mistakes hide at the edges, so test the values on both sides of a boundary.
- "`delivery_fee(50) == 0` is a test." Without `assert`, nothing checks the comparison, and the test passes whatever the function returns.

</Callout>

<Chunk n={2} title="Fixtures and parametrize">

A **fixture** is a function marked `@pytest.fixture` that builds something tests need. A test asks for it by naming it as a parameter, and pytest calls the fixture again for each test, so every test gets a fresh object. `@pytest.mark.parametrize` runs one test function once for each set of values, and reports each case on its own. Use it when the steps are the same and only the data changes.

pytest also provides built-in fixtures, such as `tmp_path`, a fresh temporary folder for each test. Tests must not depend on each other or on the order they run in. Shared state between tests gives failures that are hard to understand, and a fixture is the safe way to share set-up.

**Worked example.** A fixture and a parametrised test.

```python nocheck="needs pytest"
import pytest
from schedule import Schedule

@pytest.fixture
def schedule():                                   # a fresh Schedule for each test
    s = Schedule()
    s.book("09:00", "Amara")
    return s

def test_booked_slot_is_taken(schedule):          # pytest passes the fixture in by name
    assert schedule.guest_at("09:00") == "Amara"

@pytest.mark.parametrize("slot, expected", [("09:00", "Amara"), ("10:00", None)])
def test_guest_at(schedule, slot, expected):      # runs twice, once for each pair
    assert schedule.guest_at(slot) == expected
```

<Callout type="misconception" title="Common misconceptions in chunk 2">

- "A loop over the cases inside one test is the same as `parametrize`." The loop stops at its first failing assert. `parametrize` reports every case.
- "A fixture runs once for the whole file." By default it runs again for each test that uses it.
- "Tests can share a module-level list to save time." Then one test changes what the next one sees.

</Callout>

<Chunk n={3} title="Fakes, mocks and the clock">

Code that calls an API, an LLM or the clock is hard to test: it is slow, it costs money and its answer changes. Pass the dependency in as an argument (**dependency injection**) so a test can give the code a stand-in. A **fake** is a simple working replacement, such as a dict that stands in for a database. A **mock** (for example `unittest.mock.Mock`) records how it was called, so a test can check the calls, and a stub returns canned answers.

`monkeypatch.setattr` replaces a name for the length of one test, which helps when you cannot change the code. For time, pass `now` or a clock function, and use a fake clock. A **unit test** checks one piece alone, and an **integration test** checks pieces working together. You need both, with many fast unit tests and fewer slow integration tests.

**Worked example.** A fake clock that the test moves by hand.

```python
class FakeClock:
    def __init__(self, start: float) -> None:
        self.t = start

    def now(self) -> float:
        return self.t

    def advance(self, seconds: float) -> None:
        self.t += seconds

def is_expired(created: float, clock: FakeClock, ttl_s: float) -> bool:
    return clock.now() - created >= ttl_s

clock = FakeClock(100)
print(is_expired(100, clock, 60))   # False: no time has passed
clock.advance(60)
print(is_expired(100, clock, 60))   # True: exactly the lifetime, with no waiting
```

And a test that replaces the call to a model, so that no network is used.

```python nocheck="needs pytest"
from assistant import summarise                 # summarise calls assistant.call_model

def fake_call_model(prompt: str) -> str:
    return "CANNED ANSWER"                      # no network, no cost

def test_summary_uses_the_model(monkeypatch):
    monkeypatch.setattr("assistant.call_model", fake_call_model)
    assert summarise("a long text") == "CANNED ANSWER"
```

<Callout type="misconception" title="Common misconceptions in chunk 3">

- "More mocks mean better tests." Many mocks tie a test to how the code works inside, so it breaks when you only reorganise.
- "A fake that always succeeds is enough." It never tests the error path. Let it fail the way the real service fails.
- "Unit tests are enough." They cannot find faults between the pieces. Keep a few integration tests.

</Callout>
