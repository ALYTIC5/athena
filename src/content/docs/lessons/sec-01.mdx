## Why this matters

Cloud skills appear in 35% of the postings you are targeting, and every cloud, payment or telephony integration comes with keys. Pushing one to a public repository is a mistake that happens often, and an interviewer will ask what you do next. The OWASP Top 10 (a ranked list of web security risks from the Open Worldwide Application Security Project) is the shared vocabulary for web security, so being able to name and prevent its main risks makes you a safer person to give production access to.

## Objectives

By the end of this lesson you can:

1. Explain why a pushed secret stays compromised after you delete it, and put the incident steps in order.
2. Explain what `.gitignore`, a pre-commit hook and push protection each do and do not catch.
3. Spot leaked secrets in a repository listing and in client-side code, and choose the least-privilege option for a key.
4. Explain broken access control (A01), injection (A05) and authentication failures (A07), with one defence for each.

<Chunk n={1} title="A pushed secret stays compromised">

A **secret** is a value that grants access: an API key, a token or a database password. Git keeps every commit. A push copies them to the server, and every **clone** (a full copy of a repository) or **fork** (a copy of it under another account) made afterwards has them too. Deleting a file in a later commit only changes the newest snapshot, and the commit that contained the secret stays in the history.

So once a secret has been pushed, treat it as **compromised**: assume someone has a copy. Rewriting history removes it from your repository, but not from forks or other people's clones. Only the provider (the service that issued the key) can make the leaked value useless, by **revoking** it (switching it off) or **rotating** it (issuing a new one and switching the old one off). Check that the old value really is off, because some providers keep it working for a grace period.

That sets the order: revoke or rotate, check the provider's logs for use of the old key, purge the history if it is still worth it, then add prevention. GitHub says that after rotation, rewriting history may not be worth the effort.

**Worked example.** A synthetic file `config/.env.production` was committed in `3f9a1c2` and deleted in the next commit.

```bash
# Step 1, at the provider (not in git): revoke the key and create a new one. Then check its logs for use.
git log --oneline --all -- config/.env.production   # inspect: both commits still show up
git show 3f9a1c2:config/.env.production             # the old content is readable by anyone with the repo
# Step 3, in a fresh clone: purge. Rewrite every commit without that file (needs git-filter-repo)
git filter-repo --sensitive-data-removal --invert-paths --path config/.env.production
```

Then you **force-push** (a push that overwrites the branches on the server). Anyone who already cloned must clean their own copy. Pull request pages and cached views stay until GitHub Support removes them. GitHub's page lists the full steps and needs git-filter-repo 2.47 or later.

<Chunk n={2} title="Keeping secrets out of the repository">

The repository holds the **names** of settings. The **values** live outside it: in a git-ignored `.env` file locally, and in the platform's secret store or environment variables when the code runs. A committed `.env.example` lists the names with blank values.

`.gitignore` stops files Git does not yet record from being added. A **tracked** file (one Git already records) is not affected: untrack it with `git rm --cached`. When several patterns match, the last one wins.

No single layer catches everything. A **pre-commit hook** is a script Git runs before each commit. With **gitleaks** (a tool that scans for secrets) it checks your **staged** changes, those queued for the commit. It runs only on your machine, and `git commit --no-verify` skips it.

**Push protection** on GitHub blocks a push that contains a detected secret. By default a user with write access can bypass it with a reason, and it has to be switched on. **Secret scanning** checks the whole history.

**Worked example.** The three files that keep a repository clean.

```text
# .gitignore: the real values never get staged
.env
.env.*
!.env.example
```

```text
# .env.example: committed, names only
PAYMENTS_API_KEY=
DATABASE_URL=
```

```sh
#!/bin/sh
# .git/hooks/pre-commit: scan what is staged, abort the commit on a finding
exec gitleaks git --pre-commit --staged --redact -v
```

<Callout type="note" title="Two more rules: who can read the key, and what it can do">

Any key in code sent to a browser is public. Keep secret keys on a server you control; a provider's **publishable** key is the kind meant for the browser. Never log a secret: log a masked form, such as the last four characters.

**Least privilege** means a key gets only the access its job needs: one key per service, read-only if it only reads, limited to the repositories it uses. GitHub fine-grained tokens and Stripe restricted keys exist for this.

</Callout>

<Callout type="misconception" title="Common misconceptions in chunk 2">

- "Adding `.env` to `.gitignore` removes it from the repository." It only affects files that are not tracked yet.
- "The hook protects the whole team." It runs on one machine and can be skipped, so pair it with push protection and a scan in CI (a server that runs your checks on every push).
- "A minified or obfuscated key in JavaScript is hidden." Minifying shrinks code and obfuscating scrambles it, but the browser still has to read it, so anyone can.

<Chunk n={3} title="Three risks from the OWASP Top 10:2025">

The **OWASP Top 10:2025** is a ranked list of the most serious web application risks. Three of them come up often in interviews.

**Broken access control (A01)** means a user can act outside their permissions, for example by changing an id in a URL to read someone else's invoice. Deny by default, check ownership on the server for every request, and never rely on hiding a button in client-side JavaScript.

**Injection (A05)** happens when untrusted input reaches an interpreter, such as a database, and part of it runs as a command. Keep data separate from commands. A **parameterised query** does this: the database receives the SQL and the values separately. String concatenation does not.

**Authentication failures (A07)** mean the system accepts someone who is not who they claim to be. Defences are multi-factor authentication (a second proof besides the password), limits on failed logins, checking new passwords against lists of breached ones, and giving the same message for every failed login. OWASP advises against forcing regular password changes. A common attack is **credential stuffing**: trying leaked passwords on many accounts.

Two more matter for your work: **security misconfiguration (A02)**, such as verbose errors or unchanged defaults, and **software supply chain failures (A03)**, such as untrusted dependencies.

**Worked example.** The same hostile input, handled two ways. SQL is the language of databases: `SELECT guest FROM bookings WHERE ref = ...` returns the guests whose booking reference matches, and a `?` is a placeholder for a value.

```python
import sqlite3

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE bookings (ref TEXT, guest TEXT)")
db.executemany("INSERT INTO bookings VALUES (?, ?)", [("B1", "Amara"), ("B2", "Bo")])

ref = "x' OR '1'='1"                  # hostile input from a web form
bad = "SELECT guest FROM bookings WHERE ref = '" + ref + "'"
print(db.execute(bad).fetchall())     # [('Amara',), ('Bo',)]: the input became part of the SQL

good = "SELECT guest FROM bookings WHERE ref = ?"
print(db.execute(good, (ref,)).fetchall())   # []: the input stayed data
```

<Callout type="misconception" title="Common misconceptions in chunk 3">

- "Escaping quotes by hand is enough." OWASP treats escaping as a fragile fallback. Prefer a safe interface such as parameters.
- "If the admin page is not linked, it is protected." Anyone can request the address directly. The server must check.
- "The OWASP Top 10 lists every possible vulnerability." It lists ten categories of risk, not every bug.
